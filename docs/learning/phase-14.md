# Phase 14 — FastAPI service boundary + human-approved actions

## What was built

- **API package** (`src/quickcart/api/`): `create_app()` factory, Pydantic
  contracts (`models.py`), deterministic proposal service (`proposals.py`),
  system-status assembly (`status.py`), uvicorn CLI (`python -m quickcart.api`,
  host/port from `APP_HOST`/`APP_PORT`, default `127.0.0.1:8000`).
- **Analytics routes** read Gold through the existing `GoldReaders` (Spark
  session module-cached via `build_spark`; a test session can be injected).
  Routes: `/health`, `/api/v1/overview/kpis`, `/api/v1/trends/orders`,
  `/api/v1/stores`, `/api/v1/stores/{id}/metrics`, `/api/v1/inventory/risks`
  (`?store_id=`), `/api/v1/orders/{order_id}` (silver order + delivery,
  404 if unknown), `/api/v1/anomalies` (latest 100; `[]` +
  `X-Data-Warning` header when the Gold table is not built),
  `/api/v1/predictions/delivery/{order_id}` (404 when absent),
  `/api/v1/predictions/demand` (`?store_id=&category=`; `[]` + warning header
  when absent), `/api/v1/system/status`.
- **System status** (`status.py`): phases parsed once from `kit/TASKS.md`
  checkboxes (`done`/`in_progress`/`pending`), service up/down via one TCP
  connect per service (postgres 5432, redpanda 9092, qdrant 6333, mlflow 5000,
  0.5s timeout), Gold mart presence via `Path.exists` on the data root.
  Nothing is fabricated — down/false are reported as such.
- **Agent route**: `POST /api/v1/agent/chat` delegates to
  `quickcart.agents.service.chat(message, session_id=...)` when that module
  imports cleanly, else **503 `{"detail": "agent not available"}`** — Phase 13
  owns the service; this phase deliberately ships no fake agent.
- **Proposals (the heart of the phase)**:
  - `V004__proposals.sql`: `proposals` + `proposal_audit` (every transition,
    correlation id generated at create and threaded through all rows).
  - Deterministic RESTOCK validation (kit/03 §14.3): store exists, product
    exists, quantity positive and ≤ 500, `inventory.updated_at` within 48h,
    no open (PENDING/APPROVED) proposal for the same store+product. Rules are
    a pure function (`validate_restock`) over a `RestockFacts` dataclass.
  - Validation runs at **create** (failures → 400, nothing stored) and **again
    at approve** against the stored row; a world that changed in between
    (stale inventory, new duplicate) flips `validation_status` to `INVALID`
    and the approval is rejected with 409.
  - Approve/reject only act on the **stored** proposal (kit/03 §14.4) — the
    executor rebuilds the action from the DB row, never from request payloads.
  - Executor (RESTOCK, approve path only): in **one** psycopg transaction —
    `UPDATE inventory SET on_hand_qty += qty`, `INSERT inventory_movements`
    (`RECEIPT`, reference `AUTO_PROPOSAL:<id>`), mark `EXECUTED`; any error
    rolls back and marks `FAILED` with the error detail (audit row both ways).
  - `POST /api/v1/proposals` (201), `GET /api/v1/proposals` (`?status=`),
    `GET /api/v1/proposals/{id}` (404), `/approve`, `/reject`,
    `GET /api/v1/proposals/{id}/audit`.
- **Approval UI**: Streamlit "Approvals" page appended to
  `src/quickcart/dashboard_pages.py` — proposal queue + audit trail from the
  operational DB, graceful `psycopg.OperationalError` warning.
- **Cross-cutting**: structlog logging, `X-Correlation-ID` request/response
  middleware binding the id into log context.
- **Loader fix exposed by this phase** (`src/quickcart/db/loader.py`): the
  deterministic seed COPYs explicit identity values, which never advance the
  `GENERATED BY DEFAULT AS IDENTITY` sequences — the first application-level
  insert (the proposal executor's movement row) collided with a seeded key.
  `sync_identity_sequences` re-syncs every identity sequence to max(id)+1
  after `load_reference`/`load_history`, fixing it for all tables at once.

## Decisions recorded

- **400 vs `validation_status=INVALID`**: quantity bounds, unknown store/product
  are rejected at create with 400 (client-correctable, nothing stored);
  `INVALID` is reserved for validation that flips *after* creation, observed
  at approve time. This keeps both the kit/07 gate "proposal validation runs"
  and the "unapproved proposal cannot execute" gate testable.
- **Ruff `B008`** forbids `Depends(...)` in argument defaults, so routes use
  `Annotated[GoldReaders, Depends(_readers)]` — the modern FastAPI spelling.
- **Duplicate-open rule** excludes the proposal being re-validated at approve
  time (otherwise approval would always conflict with itself).

## Known limitations

- Analytics/prediction routes assume the **local** storage backend
  (`Path.exists` guards); under the S3 backend the not-built guard would need
  a list-based check.
- `INCIDENT`/`OPS_NOTIFICATION` proposals pass through with no deterministic
  rules and no executor (approve → `APPROVED`, never executed); only RESTOCK
  has a simulated action, per kit/03 §14.3.
- Approving an INVALID-at-create proposal is impossible (creation rejects),
  so `validation_status=INVALID` is only reachable via post-create change —
  intentional, documented above.
- The agent route depends on the Phase 13 service signature
  `quickcart.agents.service.chat(message, session_id=None) -> dict`; until
  that lands the route honestly returns 503.
