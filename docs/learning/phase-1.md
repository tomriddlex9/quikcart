# Phase 1 — PostgreSQL operational database + deterministic simulator

## What was built

A coherent transactional QuickCart source system, seeded by a deterministic simulator:

- **`docker-compose.yml` core profile**: PostgreSQL 17.11 (matches the pinned baseline), named
  volume, `pg_isready` healthcheck, localhost-only port binding.
- **Versioned DDL** (`infrastructure/postgres/migrations/`): V001 creates all 14 tables from
  `kit/04 §2` with PKs, FKs, UNIQUE constraints, CHECK-constraint status enums
  (orders/payments/deliveries/movements/riders/promotions/tickets), `NUMERIC(12,2)` money,
  `TIMESTAMPTZ` timestamps, `CHAR(3)` currency. V002 adds the index set from `kit/04 §3`.
  Identity columns are `GENERATED BY DEFAULT` so deterministic explicit-ID loads (and later
  CDC MERGE) work. A `schema_migrations` table records applied versions; `V001/V002` applied
  in one transaction each.
- **DB CLI modules**: `quickcart.db.init` (apply pending), `quickcart.db.reset` (drop/recreate
  schema — destructive, disposable test DBs per kit/05 §7), `quickcart.db.validate`
  (integrity + ordering + money reconciliation + causal sanity + determinism fingerprint).
- **Simulator** (`src/quickcart/simulator/`): `config.py` (Pydantic + YAML + CLI overrides +
  `--smoke` scale), `behavior.py` (pure causal model), `generator.py` (reference + history),
  `seed_reference.py` / `historical.py` CLIs. Causal chain per kit/05 §8:
  demand = base x hour-curve x weekend x store-multiplier x popularity x promo x weather;
  pick minutes = base + basket effect + queue effect; ride minutes = distance + rider
  shortage + weather + noise; `is_late` derived from promised-vs-actual; cancellations
  conditioned on rain/peak/shortage and expected lateness; payments with per-method failure
  probabilities and retries; inventory consumed by sales and auto-restocked via RECEIPT
  movements; support tickets derived from late/cancelled/refunded orders.
- **Load adapter** (`src/quickcart/db/load.py`): COPY-based bulk inserts; reference
  fingerprint guard (`historical` refuses to load against mismatched reference data).

## How to run

```bash
make core-up     # docker compose --profile core up -d
make db-init     # apply migrations
make seed        # full: reference + --seed 42 --orders 100000
make seed-smoke  # tiny deterministic dataset (2 stores, 500 orders)
make db-check    # validation report
```

## How to test / verification executed

- `uv run pytest`: **30 passed** — 4 unit-simulator determinism, 7 behavior, 7 in-memory
  causality, 3 integration (validation round-trip, temporal ordering, reset+reseed
  fingerprint equality), 4 contracts (numeric money columns, timestamptz coverage, status
  CHECK constraints, PK coverage), 4 smoke.
- Full seed acceptance run (seed 42, 100k budget):
  10 stores / 2,000 products / 20,000 customers / 100 riders / 8 promotions;
  **97,824 orders** (2.2% of demand unserved due to simulated stockouts), **299,918 order
  items**, 106,019 payments, 97,667 deliveries, 101,099 inventory movements, 1,622 tickets.
  Generated in **8.6s**, COPY-loaded in **11.1s** (~20s total) on this machine.
- `make db-check` at full scale: all checks PASS — 0 FK orphans, 0 timestamp violations,
  0 money-reconciliation violations; causal aggregates: peak/off-peak ratio 11.5,
  weekend 528 vs weekday 453 orders/day, pick minutes 11.6 (large baskets) vs 5.3 (small).

## What was learned

- **Determinism is a contract, not a hope**: fixed `numpy.random.default_rng(seed)` + fixed
  draw order reproduces byte-identical datasets; fingerprint guards (canonical JSON hashing)
  make drift visible. Gotcha found: psycopg returns `zoneinfo.ZoneInfo('Etc/UTC')` for
  timestamptz while the generator emits `datetime.timezone.utc` — equal instants, different
  reprs; fingerprints therefore compare canonical string forms (`json.dumps(default=str)`).
- **NUMERIC scale matters for equality**: `Decimal('19.076') != Decimal('19.076000')` —
  generated values must match the column scale (`.quantize`) to round-trip identical.
- **psycopg lazy generators + closed connections** don't mix: `fetch_all` returns a list.
- **COPY beats row-by-row** by ~an order of magnitude for 100k+-row loads.
- **The causal model produces learnable signal**: ML targets (lateness, cancellations,
  demand spikes) are driven by observable drivers, not sampled labels.

## Known limitations / decisions

- **Single local-dev DB user**: `POSTGRES_USER=quickcart_app` is the container superuser —
  a deliberate local-dev simplification (kit/06's `.env` field set). Least-privilege split
  deferred until a real multi-user need appears.
- **Status enums as CHECK constraints** (not PG ENUM types) to keep migrations simple.
- **Weather is a synthetic placeholder signal** per kit/03 §1.4 (seasonal rain/heat per
  store-day); real API enrichment arrives in Phase 9.
- **`historical` requires matching `seed_reference`** (same seed/config/scale) — enforced
  by the reference fingerprint, so a stale reference can never silently pair with new data.
- ~2.2% of simulated demand is discarded as unserved (stockout-squeezed baskets) — this is
  intentional (stock availability must affect fulfillment) and explains 97,824 vs 100,000.
- In-memory generation holds ~800k row tuples (~0.5 GB peak) — fine at this scale;
  streaming generation would be the next step if scale grows.
- This machine's host ports 5432 (native PostgreSQL) and 5433 were occupied; local `.env`
  uses `POSTGRES_PORT=5434`. `.env` is gitignored; `.env.example` keeps the generic 5432.
